Settled by design, not stuck

These read like limitations in the README but each is a decision with a stated reason. They stay off the ledger unless the reason changes.

  • The whole file sits in memory. That is what makes every frame instantly addressable. Fine to a few GB.
  • Reverse stops at 0.5× backwards. Decoders only run forward, so each step back is a seek that re-decodes most of a GOP. Faster labels would promise frames the decoder never delivers.
  • Followers are silent. Independent DACs cannot share a clock. One designated node plays audio and its hardware clock reaches the others through the re-anchor.
  • Filters are fixed strength. No blend factor, so each shader is its own target and carries no mix.
  • The copied launch URL is always a follower. Only one client may own the timeline, and a master URL pasted onto a wall would have the nodes take mastership from each other in turn.
  • MP4 and MOV only. MP4Box is the demuxer. WebM would need another one, and that is a scope decision rather than a gap.

What to do next

Proposed, in the order that unblocks the most. The first two turn the localhost-only claims into wall-tested ones; the third keeps frame-exactness honest without a human watching.

  1. Pick the secure-context path and make it the default

    WebCodecs and the Window Management API only exist in secure contexts, and plain http://SERVER:8417 from another machine is not one. The README lists three workarounds and the server offers none. The smallest fix is opt-in TLS in server.js through Node's own https module, taking cert and key paths, which keeps the zero-dependency rule. Pair it with a one-paragraph mkcert recipe.

    every real wall node, and therefore the next two steps
    packaging and proxying, tiled wall deployment
  2. Run one real wall and write the number down

    Two or more machines, one master, followers on their own displays, the beep clip looping. Read follower deviation from /status in the shared clock domain and put that figure in the README where it now says measured on localhost. The same session can settle whether the line interlace aligns on a passive 3D display at native resolution.

    the sync and interlace claims, and the aspect-fit across real bezels
    multi-client sync, GPU filters and stereo 3D, verification
  3. Automate the ground truth the clips already carry

    The burned-in frame clips are the oracle and nothing reads them automatically. A node-side check can assert the demuxer's frame table for the 300-frame clip, and a Chrome DevTools Protocol script can load the page, seek to random frames, and compare the FRAME readout with the requested index, then assert zero deviation on pause through /status. No new dependencies beyond a local Chrome.

    refactoring the player and demuxer without a human stepping through frames
    verification, frame-exact playback
  4. Let a node load a different file from the master

    Hardware decoders refuse frames beyond roughly 8192 px on a side, and the README's answer is to split per-eye files and sync them. Followers currently auto-load whatever the master announces, so that answer has no mechanism. A per-node source override in the launch URL, with the master's file kept as the fallback, would make split-eye and per-tile files possible.

    stereo above 8192 px, and pre-cropped per-tile files that avoid decoding the full frame on every node
    tiled wall deployment, GPU filters and stereo 3D
  5. Then the longer arcs, if they are still wanted

    Wall geometry in the launch-URL panel so tile, crop and fit have a live UI. Opus-in-MP4 through dOps extraction. Drop-frame timecode. Streaming through incremental appendBuffer and on-demand sample windows, which the README already sketches.

    media and transport UX, frame-exact playback, audio
